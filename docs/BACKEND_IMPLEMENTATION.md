# JobPilot 后端实现设计

逐项确认中的草案 · 2026 年 9 月 12 日

这份文档专门记录新版 JobPilot 的后端实现方案。业务范围以[需求文档](REBUILD_PRD.md)为准，Agent 的职责和工作方式单独记录在 [Agent 设计](AGENT_DESIGN.md)中。当前暂停讨论后端细节，以下只整理已经确认的决定和后续讨论入口。

## 已确认的总体方案

JobPilot 业务后端使用 **Go + Gin**。首版仍由一个 JobPilot 服务承担画像、后台任务、模型调用和 Agent 工具接口，服务内部按业务职责分模块。注册、登录和会话改由独立的共享认证服务承担；JobPilot 不因此拆分其他业务模块。

求职 Agent 的运行时、流程编排和工具调用也放在这个 Go 服务中，使用 **Eino** 实现，首版不增加独立的 Python Agent 服务。Agent 只能通过服务内部定义的业务接口访问 JobPilot 数据，不能绕过业务约束直接操作数据库。

当前业务模块包括：

- 共享认证服务接入与 JobPilot 访问权限。
- 求职目标。
- JD 与市场画像。
- 共用岗位分类和能力目录。
- 用户材料与能力评估。
- 知识短板分析。
- 项目推荐；具体实现等待推荐机制确定。
- 模型服务接入。
- 求职 Agent 助手所调用的受控业务功能。

首版固定接入 DeepSeek、Qwen、GLM、Kimi 四家模型服务。个人分析使用用户配置的 Key，共用分类审核使用平台 Key。具体模型型号和每家服务的调用适配方式仍需验证。

向量生成统一使用平台配置的一个国产 Embedding 模型和平台 Key，不跟随用户选择的生成模型变化。能力目录与用户材料只有处在同一个向量空间中才能直接比较，因此首版不允许每个用户自行选择 Embedding 模型。平台需要保存向量所用的模型和版本，模型更换后按受控流程重新生成相关向量，并对单个用户的材料数量和向量调用频率设置限额。具体 Embedding 模型通过真实 JD 的归一化准确率、稳定性和费用测试后确定。

JobPilot 的主数据库确定使用 **PostgreSQL**，并启用 **pgvector** 支持向量检索。RAG 的首要用途是辅助 JD、简历和经历材料中的能力表述归一化：根据能力目录中的标准名称、别名、定义和等级说明检索少量候选能力，减少每次归一化需要交给模型的目录内容。是否允许某些高置信匹配不经过模型直接确认，以及采用什么阈值，需要使用真实 JD 标注集验证后再定，不能只把向量距离最近的结果直接当成正确分类。

Agent 查询 JD 原文以及已经保存的简历、经历文本，是这套检索能力的次要用途，用于回答开放问题和引用判断依据。求职目标、分类目录、能力等级、任务状态、Agent 会话等确定性的业务事实仍以关系表和普通查询为准；RAG 不能覆盖或暗中修改结构化资料中的已确认事实。

共享认证服务也使用 PostgreSQL，但拥有独立的逻辑数据库和访问权限。低成本部署时可以与 JobPilot 共用同一个 PostgreSQL 服务实例，两个服务仍不能直接读取或修改对方的数据。首版不再增加 MongoDB、Elasticsearch 或独立向量数据库；以后只有出现 pgvector 无法满足的真实需求时再评估。

JD 分类、能力分析和报告生成等耗时操作采用可恢复的后台任务执行。用户提交资料后，接口先保存原始数据并创建任务，随后立即返回任务状态；JobPilot 服务内的 Worker 再执行模型调用和后续处理，页面通过任务状态展示进度与结果。

后台任务与 API 属于同一个 Go 项目，首版不增加任务微服务，也不引入 Kafka、RabbitMQ 等独立消息队列。任务状态持久化保存，至少区分等待、执行中、成功和失败，并记录必要的重试信息。服务重启后需要能够重新发现并继续处理未完成任务，不能只依靠进程内 goroutine 保存任务状态。首版可以让 API 与 Worker 在同一服务实例中运行；以后任务量增加时，再从同一代码库拆分 Worker 进程或接入独立队列。

旧项目的 [go.mod](../../jobpilot/backend/go.mod) 已使用 Go 和 Gin，可以作为经验参考。新版模块边界、依赖和数据结构仍根据本轮需求重新设计，不直接照搬旧实现。

共享认证服务从现有 [StudyFlow](../../studyflow) 的认证实现开始改造，作为 JobPilot 与后续微服务项目共同使用的独立服务。其确认范围和待定项记录在[共享认证服务设计](SHARED_AUTH_SERVICE.md)中。

认证服务的代码放在与 `jobpilot-next` 平级的独立 `shared-auth` 项目中。它拥有独立的 Go 模块、数据库迁移、接口文档、测试和部署入口；JobPilot 只通过认证接口和令牌使用共享身份。StudyFlow 保留自己的 Todo 业务，之后也改为 `shared-auth` 的接入方。

## 首版部署基线

首版线上环境使用一台低成本 Linux 云服务器，通过 Docker Compose 运行反向代理与前端静态文件、JobPilot Go 服务、独立的 `shared-auth` 服务，以及启用 pgvector 的 PostgreSQL。JobPilot 的 API 和后台 Worker 首版运行在同一个服务实例中。

JobPilot 与认证服务虽然运行在同一台服务器上，仍保持独立进程、独立逻辑数据库和网络接口边界。以后增加另一个业务项目或迁移服务器时，可以独立移动服务，不需要重新从 JobPilot 中拆出认证模块。普通用户只通过 HTTPS 页面访问，不需要在自己的电脑上安装 Docker、WSL 或 Linux。

用户上传的 PDF 和 DOCX 只作为解析输入。服务可以在请求处理期间使用内存或临时文件，解析完成后删除原文件，只把用户可查看、可修正的文字及文件名、格式等必要元数据保存到 PostgreSQL。首版不接入对象存储，也不提供原文件下载；用户需要重新解析时再次上传文件。

自动数据库备份暂不进入首版开发阶段，等核心功能稳定或准备开放真实用户时再确定。具体服务器规格、云厂商、反向代理软件和容器资源限制继续分别确定。

## 后端必须承接的业务约束

- 所有个人资料、对话、模型配置和结果按共享认证服务签发的用户身份隔离，不能只依靠前端隐藏入口。
- JD 原文先保存，再进行分类、能力提取和必要的新增分类审核。
- 分类审核明确否决与模型调用失败是不同结果，失败可以重试。
- 能力未知与 L0 分开保存；已有能力等级和依据在切换目标后继续保留。
- 资料变化后，旧报告继续保留并标记待更新，新结果成功后再替换当前结果。
- 用户 API Key 加密保存，普通页面和日志不出现完整 Key。
- Agent 只通过授权的业务功能读取或修改数据；持久化修改需要用户先确认。
- Agent 调用失败时不能把任务记录成已经成功执行。

## 已落地的市场画像业务链路

2026 年 9 月 16 日开始实现“当前求职目标 → 粘贴完整 JD → 保存原文与分析任务 → 页面查看处理状态”链路：

- 目标岗位保存求职类型、毕业年份和一个或多个目录方向；岗位大类和小类必须从数据库目录选择，显示标题由所选方向生成。旧自由文本目标会按名称迁移，无法匹配时要求用户重新选择。
- JD 必须归属于当前目标。提交时，JD 原文与 `jd_analysis` 后台任务在同一个 PostgreSQL 事务内写入，避免只保存其中一项。
- JD 对外显示 `processing`，内部任务从 `queued` 开始。Worker 已接通有效性判断、目录岗位分类和能力归一化；只有有效且与当前目标匹配的 JD 才进入市场画像。
- 开发环境使用可替换的 `identity.Resolver` 提供固定用户身份，业务服务和数据库查询已经按 `user_id` 隔离。非开发环境不会启用临时身份。
- 市场画像前端读取真实目标、JD 列表、任务状态、有效 JD 数量、按不同 JD 去重的能力覆盖数，以及独立判定后的能力要求等级；其他页面仍有原型数据。

实现目录为 `backend/`，接口和本地启动说明见 [后端 README](../backend/README.md)。

## DeepSeek 解析、分类与归一化链路

2026 年 9 月 16 日确认先只实现 DeepSeek，其他三家沿相同边界后续接入。第一版 DeepSeek 链路采用当前官方的 `deepseek-flash`，调用 Chat Completions 的非思考模式与 JSON Output：

- 用户在设置页保存自己的 DeepSeek API Key；服务端使用环境变量提供的 32 字节主密钥进行 AES-256-GCM 加密，数据库和查询接口均不保存或返回明文。
- Worker 使用 `FOR UPDATE SKIP LOCKED` 从 PostgreSQL 领取 JD 分析任务，同一代码可以在以后启动多个 Worker 实例时避免重复领取。
- Worker 领取任务时写入唯一租约凭证，并在执行期间发送心跳。服务运行时每分钟扫描过期租约；成功或失败回写必须同时匹配任务 ID、执行中状态和租约凭证，已经失去领取权的旧 Worker 不能写入结果。
- 创建任务前先在本地拦截纯网址、符号、乱码和重复内容。一次 DeepSeek 调用同时完成语义有效性判断、岗位名称、公司、求职类型、职责、能力证据、其他条件、岗位目录分类和能力目录映射。
- 后端不会直接相信模型判断：有效 JD 必须提取到足够的信息类别，职责和能力至少一类非空，能力及分类依据必须能在原文中逐字找到。无效或不完整 JD 的任务仍记为成功，但不会进入分类、能力关系和市场画像。
- 数据库内置常见岗位大类、小类、能力及 L0-L5 等级说明。模型只能返回目录代码；后端再按代码落入关系表。所有原文证据均保留用于解释。
- 每个岗位小类保存分类定义、典型职责信号、不能单独作为依据的排除信号，以及容易混淆的小类和区分规则。有效 JD 必须依据职责原文返回恰好一个主导小类，可以返回多个次要小类；每项分类同时保存逐字证据与独立理由。岗位标题、技术栈或单个关键词不能单独决定分类。
- 后端严格校验小类归属、primary 数量、职责证据和分类理由，不再静默修正模型的多 primary 结果。旧提示词生成的有效 JD 会自动重新排队；重析成功前保留旧分类，失败也不会清除旧市场画像。
- JD 与当前目标的关系先要求求职类型一致；主导分类命中任意一个目标方向即可计入市场画像，只有次要分类命中时保留作参考，分类完全不命中时排除。
- 能力要求使用匿名关系组持久化：`single` 表示指定能力，`any_of` 表示候选能力任选其一，`at_least_n` 表示至少满足 N 项。每个选项独立归一化，并保留 Function Calling、MCP Server/Client 等具体限定。市场画像对能力可覆盖的不同 JD 去重计数；`at_least_n` 的单个候选不能独立满足整组，因此不进入单项覆盖数。该统计不读取用户画像。
- 能力要求等级由独立异步任务判定，不复用基础解析阶段的旧 `required_level`。任务一次处理一份 JD 中已经归一化的能力，逐项对照该能力自己的 L0～L5 标准，保存等级、明确要求或职责推断、要求性质、逐字证据、理由和置信度。任务具备租约、心跳、过期恢复与旧 Worker 回写保护；失败不会清除能力覆盖统计或上一次成功等级。
- 市场常见等级按“能力＋JD”去重后取众数，并保留完整分布；并列众数全部展示，供知识短板比较的兼容等级取并列项中的较高等级。加分要求单独统计，不会抬高普通或必备要求的常见等级。
- pgvector 字段和目录数据已经准备好，但 Embedding 模型、候选召回阈值以及目录新增审核所使用的平台模型尚未确定。当前先把目录交给 DeepSeek 完成裁决，不声称已经启用向量召回或自动扩充目录。
