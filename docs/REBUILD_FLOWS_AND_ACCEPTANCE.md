# JobPilot 页面流程与验收说明

依据已确定需求整理的初稿 · 更新于 2026 年 9 月 11 日

这份文档把[需求文档](REBUILD_PRD.md)中的规则整理成用户操作和可检查的结果。页面名称及内容安排是设计初稿，业务规则沿用已有决定。本文是后续设计、开发和验收的依据，不表示功能已经实现或测试通过。

## 用户第一次怎样走完流程

1. **注册并登录。** 用户通过共享认证服务验证邮箱并设置密码。这个账号也可以登录后续接入的另一个项目。
2. **确定当前求职目标。** 选择岗位方向和求职类型，也可以设置“后端＋Agent 开发”这样的复合方向。
3. **配置模型。** 从 DeepSeek、Qwen、GLM、Kimi 中选择已支持的服务和型号，填写自己的 Key 并测试连接。开始 AI 分析前需要完成配置。
4. **使用求职 Agent 助手。** 登录后的各个页面都可以打开悬浮助手。助手结合当前页面和求职目标回答问题、查询资料，并在用户确认后调用会保存或修改数据的功能。用户可以新建、切换和删除对话。
5. **补充两类资料。** 粘贴目标岗位的完整 JD，同时提供简历或经历自述。两类资料可以穿插补充，已有信息不重复填写。
6. **补齐能力水平。** 系统从相关 JD 汇总所需能力，先使用已有材料评估；依据不足的部分，通过问答或用户手动设置补齐。
7. **确认画像完成。** 市场画像达到至少 10 份相关且处理完成的 JD；用户画像的必要信息和所有当前所需能力水平均已齐全。
8. **查看结果。** 用户发起项目推荐或知识短板分析。项目推荐的来源和筛选机制仍待确定，不能据本流程直接视为该模块已经完成设计。

## 页面怎样组织

登录、注册和找回密码作为独立入口。登录后的工作台与全局页面框架已按 2026 年 9 月 11 日确认的原型组织：左侧主导航、顶部当前求职目标、中间业务内容，以及可拖动和收起的悬浮 Agent。其他页面沿用这一框架，具体内容继续逐页确认。

| 页面 | 用户在这里做什么 | 最需要看清的信息 |
| --- | --- | --- |
| 工作台 | 查看当前目标和进度，进入下一步操作 | 当前目标、相关 JD 数量、用户画像缺少什么、两项结果入口 |
| 市场画像 | 粘贴 JD，查看处理结果和岗位要求 | 原文、处理状态、分类及主次关系、是否计入当前目标、能力要求及来源 |
| 用户画像 | 填写情况、提供简历和经历、补齐能力 | 已有材料、待补信息、当前相关能力的综合等级和依据、自评及补充问答入口 |
| 项目推荐 | 查看推荐、打开详情、选择项目、查看已选项目，填写意见并重新推荐 | 项目用途、推荐理由、自己的工作范围、当前选择及待验证事项；具体内容待推荐机制确定 |
| 知识短板 | 查看整体能力差距，资料变化后重新分析；进入能力验证或复习练习 | 当前水平、准备目标、判断依据、结果是否需要更新，以及当前问答模式 |
| 设置 | 管理模型配置和 Key | 当前选择的服务及型号、连接状态、遮盖后的 Key、替换和删除入口 |
| 全站悬浮 Agent | 询问当前页面和求职准备情况，让助手查询或调用已有功能 | 当前上下文、会话列表、引用依据、准备执行的操作及执行结果 |

工作台用具体缺项指引用户。例如“还需要 2 份相关 JD”“还有 Redis 未设置水平”，用户可以直接进入对应页面处理。能力处于 L0 或 L1 也属于有水平记录，不能显示成未完成。

JD 详情保留原文和归类依据，能力详情保留引用的 JD、简历、自述或问答依据。学历和工作年限等条件单独展示。

首版两个项目共用账号数据，但分别建立登录状态。用户在 JobPilot 注册后可以使用相同账号登录另一个项目；在 JobPilot 登录不会让另一个项目自动登录，退出其中一个项目也不要求同时退出另一个项目。

## 哪些状态需要让用户看懂

| 当前情况 | 页面应表达的结果 |
| --- | --- |
| 只有 8 份相关且处理完成的 JD | 市场画像未完成，说明还差 2 份 |
| 已提交 10 份，但 2 份仍在处理 | 显示 8 份已计入、2 份处理中，允许继续粘贴 JD |
| 相关 JD 已满足门槛，但某项能力待评估 | 市场画像完成，用户画像未完成，指出待补能力 |
| 两类画像完成，部分能力等级很低 | 两类画像仍为完成状态，可以发起推荐 |
| 新增相关 JD 带来了尚未评估的能力 | 保留已有等级，提示补齐新增项，用户画像暂时未完成 |
| 新增 JD 提高了岗位要求，但没有新增能力 | 用户等级保持原值；受影响的旧短板报告提示待更新 |
| 用户切换到另一个求职目标 | 显示新目标相关资料和进度，原目标资料继续保存 |
| 重新生成报告或推荐失败 | 显示失败原因，原来已经生成的结果继续可见 |
| 服务在后台分析期间重启 | 已保存的原文和任务继续保留，服务恢复后可以重新处理未完成任务 |

## 怎样验收账号和模型配置

| 操作或情形 | 应有结果 |
| --- | --- |
| 使用邮箱注册 | 能完成邮箱验证、设置密码和登录 |
| 使用不正确的验证码或密码 | 不完成验证或登录，给出可理解的提示 |
| 忘记密码并完成对应联系方式验证 | 可以设置新密码并重新登录 |
| 退出后重新登录，或换浏览器登录 | 已保存的目标、材料、能力等级和结果可以恢复 |
| 使用账号 A 请求账号 B 的资料或结果 | 无法读取或修改；不能只依赖前端隐藏入口 |
| 依次选择四家已支持的服务配置 Key | 可以测试连接并使用对应模型；不出现通用协议选择或任意 Base URL 接入入口 |
| Key 无效、余额不足或服务调用失败 | 页面说明实际能够判断的原因，不把调用失败显示成能力不足或审核否决 |
| 查看设置、普通日志和其他账号的数据 | 看不到完整 Key；替换和删除 Key 后，后续调用使用更新后的配置 |

四家模型接入都需要用本项目的实际输入验证。除了接口能返回，还要检查 JD 分类、能力归一和评估结果是否符合输入依据。不能仅用一条“你好”的返回证明业务效果已经合格。

能力目录和用户材料的向量统一使用平台 Embedding 模型生成，不随用户选择的生成模型变化。需要验证更换用户的 DeepSeek、Qwen、GLM 或 Kimi 配置后，已有向量仍可继续使用；平台也需要限制单个用户的向量生成量，并记录所用 Embedding 模型版本。

## 怎样验收市场画像

| 操作或情形 | 应有结果 |
| --- | --- |
| 粘贴完整 JD 并提交 | 原文先保存，后台处理期间可以继续录入其他 JD |
| 后台处理失败后重新打开页面 | 原文仍在，可以重试，无需再次粘贴 |
| 当前有 9 份合格 JD，再加入第 10 份 | 第 10 份处理完成且符合目标后，达到市场画像门槛 |
| 已达到 10 份，继续加入第 11 份相关 JD | 可以继续添加；新 JD 完成处理后也参与要求汇总 |
| 输入同义能力表述，如 Go 和 Golang | 汇总到同一个能力项，保留各 JD 的原文依据 |
| 同一 JD 多处提到某项能力 | 该 JD 在该能力的岗位出现次数中只计一份，原文依据可保留多处 |
| JD 要求 Go、Python、C++、Java 任意一门 | 四项能力都可覆盖这份 JD，但不把四项都解释成必须掌握 |
| JD 要求候选能力中至少掌握两项 | 单项只作为组合成员保存，不能单独计为可满足整条要求 |
| JD 中同时有 MySQL 索引和事务要求 | 汇总为 MySQL 一项，细节作为依据，不生成独立的索引、事务评分项 |
| JD 提到学历、工作年限 | 作为岗位条件展示，不加入能力测评清单 |
| 初始能力目录有某项能力，但当前相关 JD 均未提及 | 不自动加入用户必评清单 |

单一方向目标按已接受的暂定规则检查主导方向和求职类型。复合目标另用以下例子核对，避免机械地只看一个主标签：

| “后端＋Agent 开发，校招”的候选 JD | 应有结果 |
| --- | --- |
| 后端为主，但明确要求负责 Agent 应用开发，求职类型符合 | 可以计入，保存真实的主次关系 |
| Agent 应用为主，同时明确负责后端服务，求职类型符合 | 可以计入，不能因后端是次要方向而排除 |
| 普通后端岗位，只写了解大模型者优先 | 保留参考，不计入该目标的门槛 |
| 5 份普通后端 JD 加 5 份纯 Agent JD | 不能拼成符合复合目标的 10 份 JD |

## 怎样验收分类目录

| 操作或情形 | 应有结果 |
| --- | --- |
| 用已有分类或同义名称已经可以表达原文 | 直接复用，不提出新增申请 |
| 原文有依据，但现有目录无法覆盖 | 提出新增申请，由独立的分类审核 Agent 审核 |
| 新分类通过审核 | 新增到共用目录，相关原文及标签对应关系保存正确 |
| 新分类明确未通过审核 | 丢弃候选，不存成待归类项；原始资料和其他已确认内容仍保留 |
| 审核调用超时或连接失败 | 保留原文和任务状态以便重试，不作为明确否决处理 |
| 其他用户使用已经通过审核的新分类 | 可以复用目录条目，但看不到申请者的私人 JD、简历和评估资料 |
| 检查新增分类审核的模型调用 | 使用平台配置的模型和 Key；个人分析仍使用用户自己的配置 |

## 怎样验收用户画像

| 操作或情形 | 应有结果 |
| --- | --- |
| 简历或自述已包含必要的个人信息 | 先提取给用户检查，只追问缺少的部分 |
| 上传文字版 PDF 或 DOCX，修正解析内容 | 用户可以查看并纠正文本，后续分析使用已修正内容；解析结束后不保留原文件，也不提供原文件下载 |
| 经历材料足以支持一项能力水平 | 给出建议综合等级和依据，不再重复提问该能力 |
| 材料没有提及某项岗位能力 | 标为待评估，允许补充问答或手动设置，不直接记为 L0 |
| 某项能力问答已有足够判断依据 | 提前结束，给出建议等级和依据 |
| 某项能力已问到 3 题，依据仍不足 | 不继续无限追问，保留待评估并允许补材料或自行设置 |
| 用户在问答前或过程中手动设置等级 | 保存用户设置，并体现其来源是用户自评 |
| 用户把全部所需能力设为低等级 | 必填信息齐全后，画像仍能完成 |
| 当前目标不需要某项已经评估的能力 | 暂时隐藏，等级和依据继续保存 |
| JD 更新后同一能力要求变高 | 只改变岗位准备目标，不自动提高或降低用户等级 |

L0–L5 的判断对照[能力等级参考](ABILITY_LEVELS.md)。MySQL 等能力始终保留一个综合等级，不要求额外展示各知识点的分数。

## 怎样验收知识短板

| 操作或情形 | 应有结果 |
| --- | --- |
| 多数提及 MySQL 的 JD 要求 L3，少数要求 L4 | 常见准备目标以 L3 为依据，高要求单独提示并关联原文 |
| 某份 JD 没有提到 MySQL | 不把它当作 MySQL 要求为 L0，也不加入该能力要求的比较 |
| JD 表述含糊，但其他依据支持推测 | 明确标注推测，并说明所用依据 |
| 依据不足以确定要求 | 显示要求不明确，不强行指定等级 |
| 用户 MySQL 为 L2，岗位常见目标为 L3 | 展示整体差距，不据此编造用户不懂索引或事务等细分结论 |
| 用户修改能力水平、相关要求或判断材料 | 保留旧报告，提示资料已变化、待更新，由用户主动重新分析 |
| 只修改兴趣等不影响知识判断的信息 | 不要求因此重新生成短板报告 |
| 新报告生成期间，相关资料又发生改变 | 旧依据生成的结果不能作为与最新资料一致的新报告展示 |
| 切换目标后再切回 | 恢复该目标的当前报告，并检查资料是否已经变化 |
| 用户进入面试问答 | 先选择能力验证或复习练习，再选择一个当前目标相关的完整能力项 |
| 用户选择能力验证 | 页面显示当前等级和本轮要验证的下一级；按闭卷方式完成 6 道核心题，过程不显示提示和参考答案，Agent 可以追加最多 3 道追问 |
| 用户选择复习练习 | 可以查看提示、参考答案和讲解，不修改用户画像中的能力等级 |
| 一组问题涉及 MySQL 的查询、索引和事务 | 所有回答共同用于 MySQL 这一完整能力，不生成三个子能力等级 |
| 用户通过本轮能力验证 | 只能建议从当前等级上升一级；用户确认后更新画像 |
| 用户未通过本轮能力验证 | 保持原能力等级，不降低等级 |
| 用户希望一次跨越多个等级 | 需要逐级分别验证，不能在一轮中跳级 |
| Agent 对某个回答无法确定 | 可以针对该回答追问；追问总数不超过 3 道，只用于澄清或补证，不额外加分 |

首版验收当前结果的保存与更新，并增加上述两种面试问答模式；不增加历史版本浏览、完整学习课程或每日任务。

## 怎样验收求职 Agent 助手

| 操作或情形 | 应有结果 |
| --- | --- |
| 用户在任一登录后页面打开助手 | 浮动窗口在当前页面上方打开，保留页面上下文，不强制跳转到独立聊天页 |
| 用户收起助手 | 对话窗口关闭，页面边缘保留小助手入口；再次打开后恢复刚才的对话 |
| 用户新建对话 | 打开一条新的空白对话，已有对话继续保留，可以重新切回 |
| 用户打开会话列表并选择旧对话 | 显示所选对话的历史消息，不把其他会话内容混入当前窗口 |
| 用户删除旧对话 | 先展示待删除的会话并请求确认；确认后删除，取消时保持原状 |
| 用户询问“我现在还缺什么” | 助手查询当前目标及两类画像进度，准确列出缺少的 JD 数量、资料或待评估能力，并提供对应入口 |
| 用户询问某份 JD 为什么没有计入 | 助手读取该 JD 的分类、主次关系和当前目标规则，引用原文依据说明原因 |
| 用户询问某项能力为什么是当前等级 | 助手使用能力等级标准和当前用户证据解释；依据不足时明确说明，不能补造具体薄弱知识点 |
| 助手准备新增或修改用户资料 | 先展示将执行的操作和受影响内容；用户确认后才调用功能并保存 |
| 用户取消操作或没有明确确认 | 不保存、不修改数据，助手可以继续回答或调整方案 |
| 助手执行只读查询 | 可以直接返回结果，同时说明结果对应的当前目标和依据 |
| 系统功能、模型或外部服务调用失败 | 明确说明没有完成，不把失败显示成已保存、已分析或已更新，并提供合理的重试入口 |
| 用户要求助手访问其他账号的数据 | 拒绝访问；悬浮助手入口和工具调用都必须执行账号权限检查 |
| 用户尚未配置可用模型 | 说明需要先完成模型配置并提供设置入口，不假装已经生成 AI 结果 |
| 用户要求代码生成、项目陪做或完整学习计划 | 说明首版不支持该范围，保留当前对话和页面任务 |
| 用户退出后重新登录并打开助手 | 可以查看已保存的对话记录，并继续原来的交流 |
| 用户在聊天中提到新的经历、能力或偏好 | 助手可以在当前对话中使用；需要作为长期资料保存时，先展示准备写入的结构化内容并取得确认 |
| 用户没有确认助手整理出的新资料 | 不写入画像、能力等级或推荐偏好，后续会话不能把它当作已确认事实 |
| 已确认的结构化画像与旧对话表述冲突 | 以当前结构化资料为长期记忆依据，说明冲突并请用户决定是否修改资料 |

首版验收助手能否可靠完成这些受控任务，以及答案是否引用了正确资料。对话记录需要按账号和求职目标保存，并支持新建、切换和删除；切换目标时显示该目标的对话，不能自动混用其他目标的资料。跨会话长期记忆只使用已经保存的结构化资料，不从聊天记录中自动生成隐含画像。

## 项目推荐目前能确定哪些验收条件

两类画像未完成时，需要先提示补齐；完成后才能发起推荐。每轮暂定最多 3 个，合格项目不足时允许少给，二开与从零项目不固定配比。

用户可以选填调整意见并重新推荐。本次意见不自动修改画像；新结果成功后更新，生成中或失败时保留原结果。

用户可以从项目详情选择一个项目。选择成功后显示独立的已选项目状态，内容包含项目定义、主体范围、推荐理由、能力对应关系和待验证事项；返回推荐列表后仍能识别当前选择，并可以改选其他项目。选择项目不会在首版自动生成开发计划或代码。

这些只能验证进入条件和结果更新流程。候选项目来源、问题依据和筛选标准未确定前，不能对推荐质量完成验收，也不把测试用的示例项目当成正式推荐来源。

## 进入实现前还要补什么
