# JobPilot 产品需求文档

讨论草案 · 更新于 2026 年 9 月 11 日

## 产品要解决什么问题

JobPilot 面向正在准备求职，却不知道做什么项目适合写进简历、也不知道如何起步的人。他们可能接触过一些技术、跟着教程做过项目，但仍然不清楚：什么问题值得解决，什么工作能体现自己的能力，以及自己是否做得下来。

首版重点服务已有一些编程基础、但缺少拿得出手的项目经历，正在准备实习、校招或初级社招的人。他们至少接触过一门编程语言、能写简单程序，可以还没有做过完整项目。这是产品优先服务的人群，不额外设置注册门槛。

首版覆盖软件开发相关岗位，包括前端、后端、移动端、AI 应用开发等。具体能力要求由用户提供的目标岗位 JD 决定。

产品主要帮助用户做两件事：**找到值得投入的求职项目，以及了解自己的八股文知识短板。**

登录后的各个页面都可以打开一个求职 Agent 助手。它不是额外生成第三种报告，而是帮助用户使用上述功能：理解当前资料和结果、判断下一步、调用 JobPilot 已有能力完成任务。

项目推荐包含开源项目的二次开发和从零开发两种方向，重点是解决真实问题、有实际价值。二开的基础项目既可以是求职常用项目，也可以是其他适合写进简历、体量和复杂度合适的开源项目。通过有理由的改造形成特色，避免直接照搬成品，以及为了显得不同而堆功能、换技术。

首版先把这两件事做好：项目方面给出推荐和理由，八股文方面指出哪些知识还比较匮乏。帮助用户开始开发是后续方向，首版不提供详细开发计划、代码生成、陪做或完整的学习课程。

这次重新开发先明确需求，再进入设计和实现。重要的产品选择经过讨论后再确定。

## 用户怎么使用

用户通过浏览器访问 JobPilot，使用自己的账号建立两类画像。

首版每个账号维护一个当前求职目标，由岗位方向和求职类型组成，例如“后端开发＋校招”。一个目标下可以收集不同公司的相关 JD。用户可以切换当前目标，同一时间围绕一个目标开展分析。

岗位方向可以是单一方向，也可以组合已有的大类和小类形成一个复合目标，例如“后端开发＋Agent 应用，校招”。复合目标仍是一个求职目标，不为每种方向组合另建岗位分类。

**用户画像，用来了解这个人。** 它记录用户的求职目标和个人情况，供项目推荐与八股文分析共同使用。同一份信息只需要提供一次，不要求用户进入不同功能后重新填写。

需要收集的必填信息包括：

- 目标岗位和求职类型，例如实习、校招或社招。
- 已有经历；还没有相关经历时，可以明确填写“暂无”。
- 每周可以投入的时间，以及期望完成项目的周期。
- 岗位能力清单中每项能力的水平。

兴趣、技术偏好、城市和公司偏好等作为选填信息。系统优先从简历或自述中提取已经提供的内容，只询问缺少的部分。

用于建立用户画像的简历和经历，可以直接输入或粘贴文字，也可以上传文字版 PDF 或 DOCX 文件。上传文件只用于提取文字，系统把解析结果交给用户查看和纠正，并将确认后的文字及必要元数据保存到 PostgreSQL。首版不长期保存 PDF 或 DOCX 原文件，解析结束后删除临时文件。

能力评估先使用用户手头已有的经历自述、简历等材料。系统对照岗位能力清单，先判断材料足以支持的能力水平；只有材料不足以判断的能力，才通过技术知识与场景问答进一步补齐。已经能够判断的部分不重复提问。

补充问答针对每项待评估能力，先问一道技术知识或场景题，再根据回答决定是否追问。每项能力暂定最多 3 道题，已有足够依据时提前结束。系统给出建议等级和判断依据，用户可以修改。

用户可以在问答前或过程中直接设置能力水平。问完仍无法判断时，保留“待评估”，说明缺少什么信息，由用户补充材料或自行设置。材料未提及某项能力时，也先保留为待评估，不能直接认定用户不会。

能力水平使用六档，通用含义如下。用户设置等级时，还可以查看该项能力在各等级的具体说明。

| 等级 | 含义 |
| --- | --- |
| L0 | 未学习 |
| L1 | 了解概念 |
| L2 | 能在指导下完成基础任务 |
| L3 | 能独立完成常见任务 |
| L4 | 能处理复杂场景并作出技术取舍 |
| L5 | 能设计体系并指导他人 |

“尚未评估”单独标记，不属于六档中的任何一档，也不等同于 L0。

上述必填资料齐全、当前目标的每项岗位能力都有评估结果或用户自行设置的水平，用户画像就算完成。能力薄弱不影响画像完成，但当前目标所需的能力不能留着尚未评估、也没有设置水平的项目。

**市场画像，用来了解目标岗位。** 它整理相关岗位的要求，帮助判断用户应该准备哪些知识，也为项目推荐提供岗位方面的参考。

首版由用户自行找到目标岗位，将完整的招聘说明（JD）粘贴到 JobPilot。只提供粘贴录入，不提供文件批量导入或自动搜集岗位。

JD 提交后先保存原文，分类、能力提取和必要的新增分类审核在后台完成，用户可以继续录入其他 JD。页面显示处理状态；处理失败时保留原文、说明原因并提供重试，无需重新粘贴。审核调用超时或连接失败可以重试，不视为审核否决。

收集到 **至少 10 份处理完成、且与当前目标岗位相关的 JD**，就达到市场画像的完成门槛。尚未处理完成或处理失败的 JD 暂不计入。用户可以继续添加更多 JD，10 份是最低数量，不是数量上限。

生成市场画像时，系统使用全部已收集的相关 JD，从中提取能力要求，对应到数据库中统一维护的能力目录，将同义表述归到同一个能力项，形成岗位能力清单。相互关联的要求按指定能力、任选其一、至少满足 N 项三种匿名关系组保存，每个候选项独立归一化并保留具体限定和原文依据。市场画像按不同 JD 去重显示每项能力可以覆盖多少份 JD；任选项都可覆盖对应要求，但“至少满足 N 项”的单个候选不能独立算作满足整组。该统计不读取用户画像。首版先以用户提供的 JD 为依据，不额外补入 JD 没有提到的能力。

每份已计入画像的 JD 还要按统一能力目录中的 L0～L5 标准独立判定能力要求等级，并保存逐字证据、判级理由以及“JD 明确要求”或“系统根据职责推断”的来源。市场画像按不同 JD 去重汇总等级分布，以众数作为常见等级；并列时如实展示多个常见等级，供后续知识短板比较的建议等级取并列项中的较高等级。优先、加分等要求单独统计，不混入普通或必备要求的常见等级。

同一目标岗位继续添加 JD、更新能力清单后，所有已有能力等级及依据继续保留，含义未变的能力可以沿用原来的评估。岗位要求提高时，只调整准备目标，不自动改变用户当前的能力等级。

新增能力先用已有简历、自述等材料判断，不足时再通过问答或用户手动设置补齐。能力被拆分、合并或范围改变时，保留原能力的评估记录，同时说明变化，请用户补充确认新能力，避免直接套用旧等级。当前目标出现待补充项时，用户画像暂时变为未完成，补齐后恢复完成。

学历、工作年限等条件单独展示，不作为能力测评项。

两类画像都完成后，用户才能开始项目推荐。如果还有一类没有完成，就先完善画像。

画像建立后，用户可以获得两种结果：

- **项目推荐**：有哪些项目值得考虑，为什么适合自己。
- **知识短板**：对照目标岗位，自己哪些八股文知识还比较薄弱。

这两项功能共用画像，但各自回答不同的问题。岗位要求可以说明一个项目与求职方向是否相关；项目要解决的问题是否真实，还需要有相应依据。

**切换目标时，资料继续保留。** 所有已经评估或自行设置的能力等级及依据都保存在账号下。当前目标相关的能力显示并参与分析，无关能力暂时隐藏，以后切换到相关目标时可以恢复显示和使用。切换目标不会清空或自动修改已有能力等级。

简历、经历、已录入的 JD 和已生成的报告、推荐结果也按同样原则保留。当前目标只展示和使用相关内容，无关资料暂时隐藏，也不计入当前目标的完成条件。切回原目标时恢复相关内容；已有报告仍需检查依据是否变化，变化后标注待更新。市场画像的至少 10 份 JD 门槛始终按当前目标的相关 JD 计算。

## 岗位和能力怎样分类

系统在数据库中维护统一的岗位分类目录和能力目录，记录大类、小类及其归属关系。先根据市场上常见的岗位与能力整理一批初始分类，在项目初始化时导入数据库。后续归类以数据库中已有的目录为基础。

首批岗位目录已确定为后端开发、前端开发、客户端开发、AI 应用开发、数据开发、测试开发、基础软件与云平台开发、嵌入式开发、游戏开发九个大类，各类的小类见[初始目录](INITIAL_CATALOG_DRAFT.md)。

JD 原文入库后，模型先判断它属于已有的哪些大类，再判断涉及大类下的哪些小类、哪个小类占主导、哪些属于次要关联。整理好的分类标签、主次关系和判断依据，与 JD 原文一并保存。后续判断 JD 与当前目标的关系时，以这些已保存的分类信息为基础。

对于单一方向目标，JD 的筛选标准暂定为：处理完成后，主导分类与当前目标匹配，且求职类型符合的 JD，纳入市场画像并计入至少 10 份的门槛。仅与目标存在次要关联的 JD 保留作参考，不计入该门槛。

对于“后端＋Agent 开发”等复合目标，JD 的实际工作必须同时涉及目标中各个方向的职责，且求职类型符合，处理完成后才纳入市场画像。一份 JD 可以以后端为主，也可以以 Agent 应用为主，主次关系仍如实保存；不能仅因其中一个方向属于次要关联就排除。普通后端岗位只写“了解大模型者优先”，不算符合后端＋Agent 目标，可以保留参考。

复合目标的至少 10 份 JD 门槛按同一组组合条件计算，不能用 5 份普通后端 JD 和 5 份纯 Agent JD 拼成 10 份。岗位能力清单从符合该复合目标的 JD 汇总，重复能力合并，仍按完整能力项评估综合等级。

能力也采用同样的目录管理方式。JD 中的能力要求，以及简历、经历和补充问答体现出的能力，都对应到统一的能力大类和具体能力项。对同一种能力的不同说法，使用同一个标准能力项进行汇总和比较；用户已有的等级与依据继续保留。

能力评估保留在 MySQL 这样的完整能力项粒度，每项只记录一个综合等级。MySQL 不再拆成 SQL 查询、索引优化、事务等更细的能力项单独评分；JD 中针对 MySQL 的具体要求归入 MySQL，作为综合等级判断和补充问答的依据。能力目录及新增能力审核都遵循这个粒度，不因 JD 描述更具体而新增细分测评项。

能力目录同时保存每项能力在 L0–L5 各等级具体能做到什么。模型解读 JD、评估简历和经历、生成补充问答时，都参考这套说明；用户手动设置水平时也使用同一套标准，让岗位要求与个人能力可以对照。

首批 12 个能力大类和 77 项能力已确定，见[初始目录](INITIAL_CATALOG_DRAFT.md)。全部能力的 L0–L5 说明已按确认过的尺度整理到[能力等级参考](ABILITY_LEVELS.md)。能力大类用于分组，每个具体能力项各自评估一个综合等级。

归类模型先匹配已有分类及其同义名称，能够覆盖时直接复用。只有发现已有大类、小类或能力项不足以表达原文内容时，才向系统提交新增分类申请。另一个专门负责分类审核的 Agent 审核申请，通过后才将新分类加入数据库，供后续归类使用。岗位分类和能力目录都遵循这套申请、审核和入库流程。

分类审核 Agent 使用平台统一配置的模型和 API Key，由平台维护审核模型及规则，审核调用费用由平台承担。

新增分类需要同时满足三个条件：已有分类及其同义名称无法覆盖；新分类的含义和层级归属清楚；JD 或用户材料中有支持该分类的原文依据。

审核 Agent 明确判定未通过时，直接丢弃该候选分类，不写入分类目录，不保留为待归类项，也不作为 JD 或能力标签保存。原始 JD、用户材料以及其他已确认的分类和能力等级继续保留。复用已有分类在申请新增之前处理，不作为审核未通过后的处理分支。

预置能力目录用于统一分类，不会把其中所有能力都变成用户必须评估的项目。用户仍只需补齐当前目标 JD 涉及的能力。分类目录可以共用，个人 JD、简历和能力评估结果仍按账号隔离。

## 求职 Agent 助手做什么

求职 Agent 助手作为登录后全站可打开的悬浮助手存在。收起时显示为页面边缘的小助手入口，展开后显示在当前业务页面上方的浮动对话窗口；用户可以收起或再次打开，不需要离开正在处理的任务。用户在工作台、市场画像、用户画像、项目推荐或知识短板页面，都可以直接询问当前页面内容和自己的求职准备情况。

助手可以读取当前账号下与当前求职目标有关的结构化资料，包括画像完成进度、JD 原文及分类依据、岗位能力要求、用户能力等级及依据、当前分析结果。它只能访问当前用户有权查看的数据，不能读取其他账号的资料。

首版重点支持以下任务：

- 说明两类画像还缺什么，并引导用户进入对应步骤。
- 解释一份 JD 为什么计入或没有计入当前目标，引用分类标签和 JD 原文依据。
- 解释某项能力的建议等级、岗位要求和判断依据，帮助用户进入材料补充、自评或问答流程。
- 查询当前报告和推荐结果，回答用户对结果的疑问。项目推荐机制确定后，再补齐助手调整推荐条件和重新推荐的具体规则。
- 调用 JobPilot 已有功能完成任务，而不只是告诉用户应该点击哪个页面。

助手可以直接执行只读查询。需要新增、修改或删除持久化数据时，必须先向用户展示准备执行的具体操作和受影响内容；只有用户明确确认后才执行。用户取消或没有确认时，不修改数据。普通页面上由用户亲自填写并点击提交的操作，继续按页面自身的确认规则处理。

助手通过受控的系统功能读取和操作数据，不能绕过账号权限或业务规则直接修改内容。工具调用失败、模型调用失败或结果依据不足时，需要如实说明任务没有完成以及可以怎样处理，不能假装已经保存、分析或更新成功。

助手解释岗位、能力和结果时，应尽量引用当前资料中的可核对依据，让用户能区分原文事实、系统判断和信息不足。产品不向用户展示模型隐藏推理过程，只展示完成任务所需的步骤状态、所用依据和结果。

首版助手仍遵守产品边界，不扩展为通用聊天、代码生成、项目陪做、完整学习课程或每日任务系统。

助手的对话记录保存在当前账号下，用户重新登录后可以继续查看和交流。用户可以新建对话、在已有对话之间切换，以及删除不再需要的对话。删除前需要明确确认，取消时保留原对话；删除是否提供恢复能力留到实现设计时确定。

新建对话不会清空或覆盖已有对话。对话记录本身只用于恢复会话，不自动成为用户画像、能力等级或推荐偏好。

助手的长期记忆以 JobPilot 已有的结构化资料为准，包括用户明确填写或确认的求职目标、个人情况、能力等级、材料和其他画像信息。聊天中出现的新信息需要先整理成准备写入的具体内容，并经用户确认后才能保存到相应资料中；没有确认的信息不能在后续会话中当作已经确定的用户事实或偏好。

每个对话绑定创建时的求职目标，只使用该目标下的业务资料。切换目标时显示新目标下最近使用的对话，没有对话时新建；切回原目标后恢复原来的记录。首版不在同一对话中自动混用多个目标的资料。

## 项目应该怎样推荐

推荐应让用户看懂“这个项目是什么，以及为什么值得我做”。

对于**开源二开项目**，系统比较适合用户做求职作品的开源项目，分析它们的功能、设计和适用场景。项目不能简单到缺少可展示的工作，也不能复杂到超出用户的理解和完成能力。推荐的重点是找出原项目在某个具体场景下的不足，或调整项目的业务、技术侧重点，让用户做出有特色、适合写进简历的作品。

首版不提供联网搜索。候选项目、项目资料及真实问题的依据从哪里获得，暂未确定，后续与项目推荐机制一起讨论。

每个改造方向都要说明：原项目提供了什么，在哪种场景下存在不足，为什么需要这样改，用户亲自承担哪些工作，以及这些工作能体现什么能力。改造的特色需要来自具体问题和设计选择。

这里的二开以用户自己的求职作品为交付目标，不以修复社区 Issue、贡献补丁或等待上游合并为主线。原项目的文档、代码和实际使用场景可以用于分析改造理由，不要求社区已经提出完全相同的需求。

对于**从零开发的项目**，系统结合画像选择具体使用场景，确定适合用户完成的范围与侧重点。题目可以已有同类产品，重点是解决什么问题、为什么这样设计，以及能体现什么个人能力。

用户从零实现自己的系统，可以使用框架和通用库，不要求先找到一个可二开的仓库。首版只提供选题和推荐理由，说明面向谁、解决什么问题以及大致做成什么，详细实现方案留到后续。

推荐结果不应只剩项目名称、技术栈和仓库链接，也不必写成长篇开发说明。读完以后，用户应该能理解它的实际用途和个人工作，并判断自己是否愿意继续了解。

首版不提供项目收藏功能。

每轮暂定最多推荐 3 个项目，按质量和对用户的适合程度排序，不固定二开与从零项目的配比。合格项目不足时少给，并说明原因。

用户不满意结果时，可以点击“重新推荐”，并选填调整意见，例如“项目太复杂”或“想换个应用场景”。系统结合当前画像和本次意见重新推荐，意见只作为本次推荐的补充条件，不自动修改用户画像。新结果成功生成后更新页面；生成期间或失败时保留原结果。

用户可以从推荐详情中选择一个项目。选择后进入当前目标下的“已选项目”页面，查看项目要解决的问题、预期形态、自己需要承担的主体范围、推荐理由、可体现的能力和开始前仍需验证的事项。用户可以返回推荐列表查看其他项目或更换当前选择。首版在这里保存选择与推荐依据，不因为选择项目而自动生成开发计划或代码。

### 怎样判断一个项目值得推荐

“问题真实、项目质量好”是核心要求。下面提出一组判断标准供讨论，具体采用哪些标准、证据需要达到什么程度，还没有定案。

- **问题具体。** 能说清谁在什么场景遇到了什么麻烦，以及为什么现有做法还不够好。
- **个人工作明确。** 用户有需要亲自设计、实现和验证的部分，可以解释自己的贡献。
- **有值得深入的技术问题。** 技术选择服务于实际需求，能形成有依据的设计取舍。
- **范围可以承担。** 所需知识、数据和时间范围与用户已有经历及计划相符。
- **结果能够展示。** 完成后有办法演示、测试或比较效果，而不只是描述一个设想。

常见项目或相似产品已经存在，不影响它成为改造的起点；关键是改造有没有必要、个人工作是否有分量，以及用户能否解释和验证自己的设计。仓库热度和改造点数量不直接代表求职价值，缺少功能也不自动成为值得改造的理由。

推荐理由应区分已有事实和待验证的设想，不能把计划中的工作写成已经完成的成果。项目筛选的具体质量标准仍需进一步确定。

## 八股文分析做到什么程度

八股文模块比较市场画像中的岗位要求和用户画像中的知识情况，告诉用户哪些知识还比较匮乏。

JD 表述含糊、无法直接对应能力等级时，允许模型结合岗位职责、同批相关 JD 和能力等级说明，推测建议的准备等级。结果需明确标注“推测”并展示依据，让用户能区分招聘方明确要求与系统判断。依据仍不足时，显示“要求不明确”，不强行指定等级。

每项能力的主要准备目标，以提到该能力的 JD 中多数岗位的常见要求为依据，使用与用户画像一致的 L0–L5 等级。少数岗位的更高要求单独提示，并展示对应岗位和原文依据。未提到该能力的 JD 不参与该能力的等级判断。

短板结果以 MySQL 这样的完整能力项为单位展示，暂定逐项说明四件事：哪项能力需要补强、用户当前能做到什么、建议达到什么程度，以及为什么这样判断。判断依据同时展示对应的 JD 原文，以及用户自述、简历、补充问答或手动设置中的相关信息。

报告聚焦各项能力的综合等级与岗位要求之间的差距，不要求进一步诊断能力内部各知识点的薄弱程度。如果只知道当前为 L2、目标为 L3，就说明这项能力需要补强，不能据此猜测用户不会哪些具体知识点。

知识短板中增加独立的“面试问答”页面，使用 Agent 根据当前求职目标、市场画像中的能力要求和用户选择的能力生成八股问题。页面明确分成两种模式：

- **能力验证**：按面试方式闭卷作答，Agent 可以根据回答继续追问，用于验证一项完整能力是否已经达到当前等级的下一级。建立初始等级后，每轮只验证下一级；通过后才能建议上升一级，未通过则保持原等级，不能跳级或降级。能力等级仍以 MySQL 这样的完整能力项记录，不为索引、事务等题目分别打分。
- **复习练习**：允许查看提示、参考答案和讲解，用于回顾知识，不改变用户能力等级。

首版仍不生成完整学习路线，不安排课程或每日任务。一次能力验证包含 **6 道核心题，最多 3 道追问**，用于覆盖目标等级的主要方面，不能根据少量题目草率调整能力。追问只用于澄清回答或补足判断依据，不作为额外加分题。具体通过标准继续逐项确认。验证通过后的等级仍需用户确认才写回用户画像。

知识不足的判断基于画像中已经评估或设置的水平。没有填写或评估的能力仍属于待补充信息，不能直接判定为用户不会。

岗位能力要求、用户等级或判断依据发生变化后，保留上一份八股文短板报告，并标注“资料已变化，待更新”。用户修改完资料后，主动点击“重新分析”；画像仍有待补充项时，先提示补齐。

新报告成功生成、且依据仍与当前资料一致时，更新当前目标下的报告。分析期间或分析失败时仍保留并展示原报告，其他目标的结果继续保留。仅修改兴趣等不影响知识判断的信息，不要求重新分析。

首版不做历史报告功能，不提供按时间浏览历次报告或比较版本的入口。当前结果的保存、更新失败时的保留，以及切换目标后恢复对应结果仍需支持。

## 账号和在线使用

JobPilot 要做成可部署上线的多用户 Web 产品。普通用户通过浏览器使用，后台服务和数据库由服务端承担，不要求用户在电脑上安装 WSL、Linux 或 Docker。

首版使用一台低成本 Linux 云服务器，通过 Docker Compose 部署前端与反向代理、JobPilot Go 服务、独立的共享认证服务和 PostgreSQL。JobPilot 与认证服务分别运行并使用独立逻辑数据库；后台 Worker 首版与 JobPilot API 运行在同一服务实例中。上传文件不长期保存，首版开发阶段暂不实现自动数据库备份，等核心功能稳定或准备开放真实用户时再安排备份方案。

首版开放邮箱注册。

注册时，通过邮件验证码验证邮箱，再设置密码。日常使用注册邮箱与密码登录；忘记密码时，通过邮件验证码重置密码。

注册、登录、密码和会话由一个从 StudyFlow 认证模块改造而来的**共享认证服务**统一承担。JobPilot 和后续的微服务项目使用同一套账号数据和同一个稳定用户身份。首版用户仍分别进入两个项目的登录页面，不提供在一个项目登录后自动进入另一个项目的单点登录；完整 OIDC 支持留作后续扩展。

JobPilot 业务数据库不保存密码和认证会话，只保存共享认证服务提供的用户身份标识，以及该用户自己的画像、资料、配置和结果。另一个项目也只保存自己的业务数据，不直接读写认证服务数据库。

JobPilot 与共享认证服务都使用 PostgreSQL，但各自拥有独立的逻辑数据库和访问权限。JobPilot 启用 pgvector，RAG 首先用于从统一能力目录中召回候选能力，辅助 JD、简历和经历材料中的能力表述归一化；向量结果只代表相似候选，是否可以直接确认需要由真实 JD 测试决定。相同的检索基础可以供 Agent 查询用户原始资料、引用判断依据，但这是次要用途。能力等级、画像状态等已确认事实仍通过结构化数据读取，不能用向量召回结果替代。首版不增加独立向量数据库，项目候选资料是否进入检索库等推荐来源确定后再讨论。

能力目录和用户材料的向量统一由平台配置的一个国产 Embedding 模型生成，使用平台 Key 并由平台承担费用。用户选择的生成模型不改变向量空间；具体 Embedding 模型根据真实 JD 的归一化效果、稳定性和费用测试确定。平台限制单个用户的材料量和向量调用频率，避免开放注册后产生失控费用。

共享认证服务作为与 `jobpilot-next` 平级的独立 `shared-auth` 项目开发和部署。现有 StudyFlow 保留 Todo 业务，提供认证实现的改造基础，之后与 JobPilot 一样通过 `shared-auth` 使用同一套账号。

每个用户拥有自己的画像、设置、原始资料和各目标下保存的结果。不同账号之间的数据必须隔离，已保存的内容不能因为刷新、重新登录或切换目标而丢失。首版不提供历史报告浏览功能。

首版要求用户自行配置生成模型 API Key，配置后才能使用个人画像分析和项目推荐等生成式 AI 功能。这些任务的模型调用费用由用户向对应供应商支付，平台暂不提供免费生成额度。共用目录的新增分类审核以及统一 Embedding 使用平台模型和 Key，费用由平台承担。

首版固定接入 **DeepSeek（DS）、Qwen、GLM、Kimi** 四家模型服务。用户选择服务商和已支持的模型，填写该服务商的 API Key，即可进行配置。系统按厂商维护调用方式和服务地址；厂商要求地域或业务空间等专属配置时，只提示补充必要信息。

模型选择继续以国产开源型号为范围。四家服务商的接入范围已经确定，具体型号在接入时根据开源情况、服务可用性、业务效果和费用验证后确定，不默认支持某个品牌的全部型号。

**通用兼容接口和自定义模型服务接入暂缓。** 首版不提供任意填写 Base URL 接入其他服务的入口，也不要求用户选择 OpenAI 或 Anthropic 协议类型。四家服务内部采用什么接口格式，由技术设计按各厂商实际情况确定。

配置页面提供“测试连接”，让用户在开始分析前发现配置问题。四家服务分别验证本项目实际使用的文本生成、结构化结果，以及需要时的流式响应和工具调用。仅连通接口，不等于分类和能力评估效果已经合格。平台分类审核使用的具体模型，也在接入验证后确定。

API Key 随账号加密保存在服务端，用户换设备登录后可以继续使用。服务端仅在处理该用户的 AI 任务时读取并使用 Key，并限制密钥的访问权限。

设置页面只显示遮盖后的 Key，用户可以替换或删除。密钥不能暴露给其他用户，也不能出现在普通日志或公开页面中。配置失效或调用失败时，产品需要明确说明原因，让用户能够处理。

当前交付以开发者自己的求职展示为目标，支持在线演示和少量真实试用。已确认 **首年总额 500 元以内** 的预算目标，包含服务器、数据库运行、邮件、域名、平台分类审核、统一 Embedding、开发者自己的业务模型调试及机动余量。其他用户的个人生成式 AI 调用费继续由本人承担。具体分配、价格依据及测算前提见[求职展示预算](OPERATING_BUDGET.md)。部署基线已经确定为单台 Linux 云服务器和 Docker Compose；具体服务器、云厂商和模型型号仍需后续确定，自动备份暂缓。

## 接下来需要确定的事

仍未确定的核心产品选择是 **项目从哪里来、怎样筛选（暂缓讨论）**：不做联网搜索后，候选项目、项目资料和问题依据的来源；怎样判断项目体量、改造理由和真实问题的依据是否充分。

模型接入范围已确定为 DeepSeek、Qwen、GLM、Kimi 四家，通用兼容接口暂缓。具体可选型号和平台审核模型在接入验证时按效果与预算确定。

文档中已经讨论并接受的暂定规则，例如画像补充问答中每项能力最多 3 道题、每轮最多 3 个推荐，继续作为首版基线，不因保留“暂定”字样就重新逐项确认。面试问答中的能力验证是独立流程，每轮使用 6 道核心题并允许最多 3 道追问。实现验证发现问题时再调整。

已确定业务的页面组织、用户操作和验收场景已整理为[页面流程与验收说明](REBUILD_FLOWS_AND_ACCEPTANCE.md)。页面组织是设计初稿，验收场景按本需求文档整理，尚未执行。

JobPilot 后端方案已确认采用 Go + Gin，首版由一个业务服务承担画像、后台任务和模型调用，内部按功能分模块；账号认证由两个项目共同使用的独立认证服务承担，详见[后端实现设计](BACKEND_IMPLEMENTATION.md)和[共享认证服务设计](SHARED_AUTH_SERVICE.md)。求职助手和分类审核 Agent 的详细规则集中记录在 [Agent 设计](AGENT_DESIGN.md)。

前端页面与交互继续在[前端设计](FRONTEND_DESIGN.md)中逐项确认。主数据库已经确定为 PostgreSQL，JobPilot 使用 pgvector，RAG 首先服务于材料中的能力归一化，并可复用于 Agent 查询已保存的材料文本；耗时分析由 JobPilot Go 服务内的可恢复后台 Worker 执行，任务状态持久化保存，首版不增加任务微服务或独立消息队列；线上使用单台 Linux 云服务器和 Docker Compose。之后还需完成数据表和接口、RAG 具体规则、后台任务具体规则、部署配置和具体测试安排。这些工作按当前需求整理，涉及新增功能、改变现有行为或超出预算的选择时再确认。

项目推荐机制尚未确定，推荐模块暂不能完成设计和质量验收；账号、画像、分类和八股文分析等已确定模块可以继续进入页面与技术设计。开发排期在明确实现方案后安排。
