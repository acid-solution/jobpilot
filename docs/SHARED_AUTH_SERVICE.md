# 共享认证服务设计

逐项确认中的草案 · 2026 年 9 月 12 日

## 为什么单独做

JobPilot 和后续的分布式微服务项目都需要注册、登录和用户身份。两边分别维护账号会产生重复实现，也无法让同一个人稳定地使用同一身份。因此，将现有 StudyFlow 的认证部分改造成独立共享服务，作为两个项目共同依赖的基础服务。

这个拆分有明确业务理由：认证服务负责“这个人是谁”，每个业务项目负责“这个人在本项目中有什么资料、权限和行为”。JobPilot 本身仍保持一个 Go + Gin 业务服务，不为了展示微服务继续拆散画像、推荐和 Agent 模块。

## 已确认的首版范围

- 两个项目真正共用同一套账号数据和稳定用户身份。
- 用户使用邮箱注册、登录和重置密码。
- 认证服务负责密码、验证码、账号状态、登录会话、Access Token、Refresh Token、刷新轮换和退出撤销。
- JobPilot 和另一个项目分别保存自己的业务数据，只记录认证服务提供的用户身份标识。
- 两个项目不能直接读取或修改认证数据库，只能通过认证接口和经过验证的令牌使用身份。
- 首版两个项目分别登录，不提供一处登录后另一处自动登录的单点登录。
- 完整 OIDC、第三方应用授权和开放平台能力暂缓。

## 项目与仓库边界

共享认证服务作为与 `jobpilot-next` 平级的独立 `shared-auth` 项目开发，拥有自己的 Go 模块、配置、数据库迁移、接口文档、测试和部署入口。它可以独立启动和发布，不与 JobPilot 业务后端编译成同一个程序。

现有 `studyflow` 保留 Todo 业务，并作为认证实现的改造来源。可复用的账号、密码、令牌和 Session 逻辑迁入 `shared-auth` 后，StudyFlow 再改为通过认证接口使用共享账号。JobPilot 和后续微服务项目也都是 `shared-auth` 的接入方，不复制一套新的账号表和登录逻辑。

首版 `shared-auth` 与 JobPilot 部署在同一台 Linux 云服务器上，由 Docker Compose 分别运行两个服务。共同部署只用于控制求职展示阶段的成本，不改变服务之间的网络接口和数据库访问边界。

## 从 StudyFlow 复用什么

现有 StudyFlow 已经包含 bcrypt 密码哈希、注册登录、短期访问令牌、刷新令牌、服务端 Session、刷新令牌轮换和退出撤销。这些代码和分层思路作为改造起点。

改造时需要移除 Todo 业务耦合，增加邮箱验证、密码重置、多应用识别、统一外部用户身份、登录限流和安全审计。当前使用共享 HS256 密钥并在每次请求中直接查询 Session 数据库的方式，也需要根据微服务边界重新设计；具体令牌签名、验签和撤销策略继续逐项确认。

## 服务边界

共享认证服务确定使用 **PostgreSQL** 保存认证数据。它与 JobPilot 使用独立的逻辑数据库和数据库账号；低成本部署阶段可以运行在同一个 PostgreSQL 服务实例中，但不能因此开放跨库直接读写。

共享认证服务保存：

- 账号和经过验证的邮箱。
- 密码哈希、账号状态和安全相关时间。
- 登录会话及刷新令牌状态。
- 接入应用及其必要配置。
- 认证安全日志。

JobPilot 保存：

- 求职目标、JD、市场画像和用户画像。
- 能力等级及依据、知识短板和项目推荐。
- Agent 对话和用户自己的模型配置。
- 与共享身份关联的业务数据。

另一个微服务项目保存自己的业务资料和业务权限。两个项目之间不共享业务表。

## 用户操作结果

用户在 JobPilot 注册后，可以使用同一个邮箱及密码登录另一个项目。首版每个项目拥有自己的登录状态，因此用户仍需在另一个项目再次登录。两个项目取得的是同一个稳定用户身份，但访问令牌需要能够区分目标应用，避免一个应用的令牌被其他应用错误接受。

## 还需要逐项确定

- 浏览器、业务后端与认证服务之间的具体登录链路。
- 令牌签名、公钥发布、有效期和撤销策略。
- 用户身份标识的数据类型与生成方式。
- 邮件验证码提供方、频率限制与费用控制。
- 应用注册、应用级权限和管理员能力。
- PostgreSQL 数据表、接口契约、错误码、审计、测试和部署方式。
