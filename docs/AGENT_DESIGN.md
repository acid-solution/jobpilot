# JobPilot Agent 设计

逐项确认中的草案 · 2026 年 9 月 11 日

这份文档专门记录求职 Agent 助手和系统内部 Agent 的产品职责、工作方式、工具、记忆、可靠性与评测。具体编程实现留在[后端实现设计](BACKEND_IMPLEMENTATION.md)中。当前先保留已经确认的内容，其他问题后续逐项讨论。

## 面向用户的求职 Agent

求职 Agent 是贯穿 JobPilot 的使用入口，用于串联市场画像、用户画像、能力评估、知识短板和项目推荐。它不是一个与业务资料脱离的通用聊天机器人，也不是第三种分析报告。

登录后的所有主要页面都可以打开悬浮 Agent。助手收起时保留页面边缘的小助手入口，展开后以浮动对话窗口覆盖在当前业务页面上方，并且可以再次收起。助手能够读取当前页面、当前求职目标以及当前账号有权访问的业务资料，回答用户对资料和结果的疑问，并调用 JobPilot 已有功能完成任务。

首版 Agent 使用 **Go + Eino** 实现，运行在 JobPilot 的 Go + Gin 业务服务中，不单独部署 Python Agent 服务。项目的 Agent 价值主要体现在上下文选择、任务编排、受控工具调用、依据引用、修改确认和结果评测，而不是增加服务数量。

## RAG 在 Agent 中的作用

JobPilot 使用 PostgreSQL 与 pgvector 建立检索能力。RAG 的首要用途是为 JD、简历和经历材料中的能力归一化检索已有能力候选，能力目录中的标准名称、别名、定义和等级说明构成主要检索知识库。向量召回结果只是候选，不能因为相似度最高就直接视为正确分类；直接确认与模型裁决的边界等待真实 JD 准确率测试后确定。

能力目录和用户材料统一使用平台配置的一个国产 Embedding 模型生成向量，费用由平台承担。用户在设置中选择的生成模型不改变向量空间，避免为不同用户重复维护互不兼容的能力目录向量。具体 Embedding 模型后续通过真实材料验证后确定。

Agent 查询用户自己的 JD 原文以及已经保存的简历、经历文本，是这套检索能力的次要用途。检索结果必须保留来源资料及文本位置，供 Agent 回答开放问题或解释判断依据时引用。

RAG 不能取代结构化业务查询。求职目标、画像进度、能力等级、JD 是否计入市场画像等确定信息，Agent 必须通过受控业务工具读取。检索个人资料时必须先按用户身份和当前求职目标过滤，不能从其他账号或无关目标的资料中召回内容。项目候选库是否纳入 RAG，等项目推荐来源确定后再决定。

### 新对话的下一步建议

用户新建对话时，助手不使用固定欢迎语，而是主动生成当前最值得执行的下一步建议。建议至少依据以下信息：

- 当前求职目标。
- 用户新建对话时所在的页面。
- 市场画像的完成进度和具体缺项。
- 用户画像的完成进度和具体缺项。

建议需要给出一个明确动作并说明后续顺序。例如，工作台可以提示先补充 2 份相关 JD，再完成剩余能力评估；在市场画像页面新建对话时，则优先给出与 JD 收集和处理有关的建议。生成建议属于只读分析，不会修改任何业务资料。

前端原型阶段先用确定性规则和模拟状态生成建议。后端接入后仍保留相同行为，但输入改为当前账号的真实求职目标、页面上下文和两类画像状态；资料不足时需要明确指出缺失内容，不能编造进度。

首版重点支持：

- 查询两类画像进度，说明还缺哪些信息。
- 解释 JD 是否计入当前目标，并引用分类信息和原文依据。
- 解释能力等级、岗位目标和判断依据，引导用户补材料、自评或回答问题。
- 在知识短板的面试问答页面中，按用户选择的能力生成问题，并根据回答进行必要追问或讲解。
- 查询当前短板报告和项目推荐，解释结果；推荐机制确定后再补充调整条件和重新推荐规则。
- 在用户确认后，将聊天中明确的新信息整理并写入相应的结构化资料。

只读查询可以直接执行。新增、修改或删除持久化数据前，助手需要展示准备执行的操作和受影响内容，获得用户明确确认后再调用相应功能。用户取消或没有确认时不修改数据。

助手不能绕过账号权限、画像完成条件、分类规则和其他业务约束。工具或模型调用失败时，需要明确说明任务没有完成，不能伪造已经保存、分析或更新成功的结果。

## 依据与解释

助手回答岗位、能力和推荐相关问题时，需要尽量引用当前资料中的可核对依据，并区分：

- 用户或 JD 明确提供的事实。
- 系统根据多份资料作出的判断。
- 依据不足、仍需用户确认的内容。

产品展示执行步骤、工具状态、引用依据和最终结果，不展示模型隐藏推理过程。

## 面试问答中的 Agent

面试问答是知识短板中的独立页面，使用 Agent 生成和推进题目，但不把整场问答塞进全站悬浮窗口。全站悬浮助手仍可解释当前题目和页面状态，正式作答过程留在面试问答页面中。

面试问答明确分为两种模式：

- **能力验证**：根据当前求职目标、市场画像要求和所选能力组织闭卷问题。建立初始等级后，每轮只验证当前等级的下一级，并使用多道题覆盖目标等级的主要方面。Agent 可以针对用户回答继续追问，最后只对所选完整能力给出判断，不产生更细知识点的能力分数。通过后只能建议上升一级，未通过保持原等级，不能跳级或降级。
- **复习练习**：根据相同依据出题，允许提供提示、参考答案和讲解。这个模式用于复习，不修改用户画像中的能力等级。

同一项能力可以通过不同问题覆盖多个知识内容。例如 MySQL 可以问到查询、索引或事务，但所有回答共同服务于 MySQL 的综合判断，不能分别生成子能力等级。每轮使用 6 道核心题，并允许 Agent 根据含糊或依据不足的回答追加最多 3 道追问。追问用于澄清或补证，不作为额外加分题。Agent 不能根据一两道题直接改变能力；验证通过后先展示建议等级和依据，经用户确认后才写回画像。评价规则继续逐项确认。

## 对话与长期记忆

对话记录按账号保存，用户重新登录后可以查看并继续交流。首版支持新建对话、切换已有对话和删除旧对话。新建对话不覆盖已有记录；删除对话前需要明确确认。删除后的恢复方式留待实现设计。

长期记忆只使用 JobPilot 已保存的结构化资料，例如求职目标、个人情况、能力等级、材料和用户确认过的偏好。聊天中出现的新信息不会自动修改画像；助手需要先整理出准备保存的内容，经用户确认后才能写入。

每个对话绑定创建时的求职目标，只使用该目标下的 JD、画像、能力和结果作为业务上下文。用户切换求职目标后，助手显示新目标下最近使用的对话；该目标还没有对话时新建一条。切回原目标后恢复原来的对话记录。首版不在同一对话中自动混用多个目标的资料，跨目标比较以后作为明确功能单独设计。

## 系统内部 Agent

分类审核 Agent 与面向用户的求职 Agent 是两个不同角色。分类审核 Agent 只负责审核岗位或能力新增分类申请，使用平台配置的模型和 Key。审核通过后新增共用目录；明确否决时丢弃候选；调用失败时保留任务以便重试。

是否还需要其他专用 Agent、是否采用多个 Agent 协作，当前不增加结论。首版优先确保面向用户的主 Agent 能可靠完成受控工具调用。

## 首版边界

首版不把助手扩展为通用聊天、代码生成、项目陪做、完整学习课程或每日任务系统。除已经确认的面试问答外，它服务于 JobPilot 已确定的求职资料整理、画像、分析和推荐流程。
