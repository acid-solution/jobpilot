# 招聘材料识别与分阶段处理

2026-10-17

用户可以直接粘贴招聘网页文字，不必清除广告、导航、公司介绍、重复内容，也不必手工用分隔符拆岗位。材料最多 100,000 字符，最多识别 50 个候选；超限返回明确错误。约 8,000 字符的窗口保留约 1,000 字符重叠，已成功窗口保存检查点。

模型先判断是否存在招聘职责或应聘要求。小说、简历、技术文章、新闻和随机文字即使包含技术词，也不能据此生成 JD。没有有效岗位时，导入状态为 `empty`，页面显示“未识别到有效 JD”，不会创建正式 JD。缺标题、公司等字段可以继续提取；只有要求、没有职责的文本可以提取能力，但会保留明确的分类错误。

单候选直接导入；多个候选默认不选，由用户查看名称、公司和原文后确认。修改已有记录也先识别；多个候选只能选一份更新原 ID。原始材料和未选候选继续保留，可以通过导入会话查询。再次粘贴相同的多岗位材料时，仍未导入或对应记录已删除的候选可以重新选择；有效的已有记录不会重复创建。删除后重新提交单岗位材料会复用识别结果，重新创建正式 JD；删除本身不会触发自动重新导入。

## 接口

| 接口 | 结果 |
| --- | --- |
| `POST /api/v1/jd-imports`，`{raw_text,replacement_jd_id?}` | 保存材料并启动识别 |
| `GET /api/v1/jd-imports` | 当前目标最近 50 份尚未确认材料 |
| `GET /api/v1/jd-imports/:id` | 读取识别状态、错误码与候选原文 |
| `POST /api/v1/jd-imports/:id/confirm`，`{candidate_ids:[]}` | 幂等导入所选候选，标明创建或重复的 JD ID |
| `POST /api/v1/jd-imports/:id/retry` | 重试识别，复用已完成窗口 |

兼容的 `POST /jds`、`POST /jds/batch` 和编辑接口统一使用导入会话协议，响应为导入会话，不再走直接创建正式 JD 的旧路径。正式 JD 的 `/jds/:id/retry` 始终进入分阶段分析队列。已有 JD 查询接口和 ID 保持可用。Agent 添加、批量、编辑同样创建导入会话，使用 `jd_imports`、`jd_import` 查询；用户选定后，`jd_import_confirm` 仍经过原有动作确认。

## 处理与恢复

内容提取只提取基础字段、职责、技术要求及其组合关系、其他条件。模型引用原文片段编号，后端产生引用。有效要求组先保存，无效组最多追加一次局部纠正。保留 `single`、`any_of`、`at_least_n` 与必备、加分性质。

岗位分类与能力归一化分别保存。分类先复用目录，缺项时提出新增申请并独立审核；没有合法分类时保留提取内容。能力先匹配名称和别名，再通过目录文本召回和模型判断身份；配置向量服务时增强召回。漏项或不合法的归一化决策最多局部纠正一次，仍无合法结论的有效能力交由独立审核，不能静默删除。

新增能力审核、分类审核、判级的技术故障保留错误和重试入口。能力审核的业务拒绝会删除能力关联，并清除空组或无法满足原门槛的组合组；原始要求可从阶段记录追溯。判级失败不撤销提取、分类与能力结果。

阶段按原文版本保存，写入需要有效租约和版本匹配。自动重试限制每阶段最多三次并退避，人工重试只重开失败阶段。已成功阶段和窗口不会重复生成。已删除旧一次性分析器、独立归一化 Worker 和专用仓库。迁移 `00044` 停用旧队列触发器，保留历史任务记录，将尚未结束的旧任务标记为停用，不自动付费重跑。用户显式重试历史有效 JD 时，事务内将原有提取和分类结果转为阶段检查点，复用它们执行归一化；失败时保留旧业务结果。

JD 响应的 `analysis` 包含阶段状态、错误、次数、原始技术要求、分类依据、`has_pending`、`next_poll_ms`。市场页以一次 JD 列表读取作为统一数据源，约两秒轮询活动任务；服务器可建议更长等待。页面重新可见或聚焦时重读，旧请求结果不能覆盖新状态。完成后列表、详情、画像进度和能力清单一起更新。前端通过查询获取完成状态，当前没有新增完成推送通道。

目标匹配与十份相关 JD 门槛沿用原规则。不符合目标是正常筛选结果。后续报告仍需满足审核与判级就绪条件。

## 验证

固定语料与可选真实模型测试位于 `backend/internal/storage/postgres/jd_corpus_live_test.go`。正常测试不发送外部请求；设置 `RUN_JD_CORPUS_LIVE=1` 才运行 50 段基础阶段评测，`RUN_JD_PIPELINE_LIVE=1` 复用其中样本执行实际 Worker、审核和判级。均应指向隔离 PostgreSQL，并通过本机忽略的 `.env.local` 或后续凭据提供器读取模型配置。结果见[评测记录](JD_PARSING_EVALUATION.md)。

前端常规无头自动化使用 Playwright：设置 `RUN_MARKET_E2E=1` 后执行 `npm run test:e2e`，覆盖默认选择、非 JD、异步完成、过期响应和失败阶段重试。可用 `PLAYWRIGHT_CHROMIUM_EXECUTABLE` 指定本机 Chrome/Edge，未指定时使用已安装的浏览器或 Playwright Chromium；CI 会安装 Chromium 后执行。测试通过本地假接口模拟 Worker 的状态变化，不调用 Computer Use 或模型服务。

线上验收脚本为 `frontend/scripts/verify-market-live.mjs`。显式设置 `RUN_MARKET_LIVE=1`、`JOBPILOT_BASE_URL`、`JOBPILOT_TEST_ACCOUNT_FILE`、`JOBPILOT_TEST_CORPUS_FILE` 后执行；账号必须是独立的 `example.test` 普通测试账号，语料使用已授权的固定评测文件。脚本实际操作线上页面，核对默认不选、多候选确认、后台完成后详情/画像/能力自动更新。默认保留数据；仅设置 `RESET_MARKET_SYNTHETIC_FIXTURE=1` 时重置该账号已创建且严格匹配的蓝鲸科技合成 JD，以复用同一份材料重新验证处理。凭据文件必须保存在仓库外，脚本不输出密码或令牌。
